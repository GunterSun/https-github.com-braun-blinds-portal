# V5 统一订单关联与增量迁移设计 v0.1

关联 BRN-002/004/008/010/016。基于 PR #301 的关系审计；本文件及 SQL 是待实施设计，不是生产升级包。

## 第一批最小数据变化

继续使用 `orders.id` 作为不可变主键。展示订单号、旧订单号、发票号独立保存，不改号、不重建旧订单。

| 草案表 | 作用 | 必须遵守的约束 |
|---|---|---|
| v5_order_sources | 外部/旧系统记录到 orders.id 的显式映射 | 来源系统＋实体类型＋原始 ID 唯一；审核人和理由必填；不能按姓名或相似地址自动绑定 |
| v5_order_window_links | 统一订单明细连接窗口与所采用测量版本 | 同一明细绑定一次；客户、订单明细和测量窗口必须一致；允许窗口在后续补单再次出现 |
| v5_order_document_links | 报价版本、账单、旧发票版本、工厂生产单、履约单归属 | 文档类型＋文档 ID 唯一；一个文档归属一张订单；保留现有各文档编号与版本 |
| v5_order_relation_events | 关联操作审计与幂等依据 | 操作者、原因、前后值和唯一请求键；必须与业务写入同事务 |

SQL 草案位于 [proposals/order-relations.sql](proposals/order-relations.sql)，刻意不放入 `drizzle/`，不会被现有迁移流程自动执行。无历史回填、删表或已有字段重命名；没有修改应用 schema 或业务接口。

项目不持有唯一订单 ID：一个项目可有多笔订单，一个窗口可有维修/补单。一个订单可包含同一客户多个项目；每条窗口关联能反查项目与房间。如果未来允许跨客户合单，需另行设计，当前拒绝。

文档映射是第一阶段兼容层，不是把所有业务塞入一张表。供应商费用、付款和分包明细仍各自建模。安装已有真实 order_id，应复用；导入账本的可空 order_id 保留，不强迫未匹配记录随意入单。

## 新旧数据如何进入

新建：服务端一次接收客户、项目/窗口、报价来源和幂等键；创建统一订单与明细，再保存来源映射和事件。失败必须整批回滚，不允许先建半张订单后返回“成功”。同键不同载荷返回冲突，同键同载荷返回原结果。

历史：先导出只读候选清单，人工明确选择源记录和目标订单；程序核验 ID 存在、客户及窗口范围、重复映射、币种和已签发版本。无可靠客户 ID 的旧 customer_orders 只能列为待审核，不用 email 自动完成绑定。审核后在单一事务写映射和事件，不改旧单内容。映射并不意味着旧金额与新金额已对账。

历史整单跨多个新订单、合并多个客户、发票跨单等情况初版拒绝，保留待处理，不丢失原记录。数量拆分在后续独立 allocation 模型处理，不能把一条映射写给多个订单。

## API 与同步契约（待实现）

- `POST /api/v5/order-links/preview`：仅 Owner；只读返回可关联/冲突及证据，不返回密码、session 或无关客户数据。
- `POST /api/v5/order-links`：仅 Owner；要求审核理由、来源版本、订单版本及 Idempotency-Key。复核预览时的数据仍有效，原子写关联、事件与版本递增。
- `GET /api/v5/orders/:id/timeline`：在统一订单权限范围内读版本和状态事件；工厂/安装员不能读取销售价格或利润。
- 创建正式生产及生产状态切换统一调用门槛服务；旧 API 也必须调用，不能通过旧入口绕开。
- 第一版使用请求内事务＋持久事件，不依赖浏览器串行调用“保存报价→保存生产单”。外部通知后续用 outbox 和重试；通知失败不能产生重复订单。

上述路径尚未创建。实施前需确定 D1 原子批处理中的条件写入方案以及冲突版本存储，不能把先 SELECT 再普通 INSERT 当作并发安全。

## 生产门槛：固定用户已确认规则

要求当前有效的客户确认报价，实际到账净额达到该报价的应收定金；订单级调整须明确金额、理由、权限和版本。缺失金额不能默认为零；明确零定金必须有确认记录。

有效现金净额 = 已入账成功收款 − 关联退款/冲正。Credit 仅影响应收，不计现金；pending/failed 不计。多币种不直接相加，首版只接受与报价币种一致的资金，其他款项进入待核对。收款不能跨账单重复分配。

门槛必须覆盖工厂单创建/放行、工厂状态切换、orders 的 in_production 转换和未来批量接口。正式下单写入批准凭据：order_id、报价版本和哈希、定金要求、有效收款依据、操作者及时间；凭据与生产单原子保存。订单级收款可放行多家供应商，不把同一笔定金错误当成逐工厂重复收取要求。

报价变更或退款发生在正式下单前，重新校验；发生在正式下单后保留原文件和批准凭据，生成异常或变更流程，不静默撤销既有生产事实。部分生产、发货和安装按明细聚合，不直接覆盖整单为完成。

## 修改与文档保护

客户主数据用于新草稿带入；旧签发快照保持原样。窗口测量更新产生新版本；订单采用哪个测量版本必须明确，不能“最新版本”自动替换已下单尺寸。报价人工改价记录原价、改后价、原因及批准者；三套计算器各保留规则版本，不合并价格算法。

初版 SQL 禁止映射原地 UPDATE，但这不等于不可篡改：DELETE、父表变更和直接数据库权限仍需服务限制。正式实现关联纠错时必须设计撤销/替代记录，保留完整历史；不能简单删除再插入当作正常操作。当前草案不提供纠错 API。

## 演练与回滚界限

本轮测试使用内存 SQLite 和虚构记录：重放现有迁移，再执行新增草案，比较所有原业务表数据，验证跨客户/明细/测量错误、重复来源/文档、后续补单、外键、审计 JSON 和幂等约束。

限制：SQLite 单机演练不证明 Cloudflare D1 事务/并发行为。多态 document_id 的存在性、来源实体存在性、权限与角色、旧父表后续修改、映射与审计原子性尚由未来服务实现。草案不是生产就绪迁移。

上线前必须取得完整数据库/R2/配置恢复材料，使用完整脱敏历史副本演练，逐单对账并验证孤儿引用、跨客户关系及报价金额。发布应先启用只读预览，再受控启用新写入口。新数据已写入后不得通过删表回滚；关闭新入口，保留关联与事件，采用前向修复或经验证的完整恢复流程。
